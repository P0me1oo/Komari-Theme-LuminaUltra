# Lumina 网络识别

版本：0.6.0。作者：P0me1oo。配套主题：LuminaUltra 1.15.0 及更新版本；旧主题 1.14.x 可继续使用原有功能。

一个插件提供两项独立功能：

- **IP 信息与标签**：后台通过所选的 IPinfo 或 IPregistry 查询全部节点已配置的 IPv4、IPv6，主题分别展示 ASN、运营商 / 机构、IP 类型标签。
- **三网回程检测**：只对选定节点执行 NextTrace，目标跟随主题的主页延迟探测点。

两项功能不共用服务器选择、自动更新开关、更新间隔、手动刷新入口或游客权限。无需额外安装第二个插件，也无需修改 Komari 主程序。

## 安装与升级

1. 上传 `Lumina-Network-Plugin-v0.6.0.zip` 到 Komari 后台插件管理并启用。插件使用内部管理调用和自身数据存储能力，不需要单独安装 Node.js。
2. 上传并启用 `Komari-Theme-LuminaUltra-v1.15.0.zip`，主题设置即可选择 IPregistry 并填写密钥。
3. 打开主题设置，在“IP 信息与标签”选择来源；使用 IPregistry 时填写自己的 API 密钥。调整三个标签总开关后，点击页面顶部的“保存设置”，再点击“刷新 IP 信息”。需要向游客展示时，单独开启“允许游客查看 IP 信息”。
4. 只有需要回程检测时，才需要在参与检测的 Linux 节点上安装 [NextTrace](https://github.com/nxtrace/NTrace-core)，提供 GNU `timeout`，并允许 Komari 探针执行远程任务。仅查询 IP 标签不需要这些条件。

升级到 0.6.0 后默认继续使用 IPinfo；使用新增的主题密钥输入框需同时升级主题至 1.15.0。原有回程节点选择、间隔和 IP 设置保留；旧自定义地址停止使用，按主页探测点重新检测。未设置主页探测点时不会自动使用内置地址。不同来源的缓存不混用，切换来源后会重新查询。三个标签总开关默认开启，IP 信息的游客权限默认关闭，不继承回程游客权限。旧主题的合并检测入口保留地址兼容，但只触发回程，不同时刷新 IP。

## IP 信息与标签

### 查询范围与来源

- 不提供服务器选择，自动查询全部节点已配置的 IPv4、IPv6；节点未参加回程检测或暂时离线，不影响后台查询其已知 IP。
- 默认使用 IPQuality 使用的 IPinfo 演示查询接口，无需密钥；也可选择 [IPregistry](https://ipregistry.co/docs)，使用自己的 API 密钥。
- IPregistry 使用单 IP 查询接口，IPv4、IPv6 均受支持，一次返回 ASN、机构和类型，不额外调用 ASN 查询接口。计费与额度遵循 IPregistry 账户规则。
- 密钥保存在 Komari 插件配置中，由后台通过 Authorization 请求头发送，不写入查询网址、结果缓存或游客接口。主题输入框使用密码样式；切回 IPinfo 时保留已填密钥，IPinfo 请求不携带它。
- 选择 IPregistry 时密钥必填。密钥无效、额度不足、访问受限或接口格式变化会显示查询失败；更正密钥并保存后可手动刷新。
- 所有查询由 Komari 后台完成，浏览器只读取缓存。一次只使用选中的来源，不自动切换，也没有人工修改分类功能。

### 三个独立总开关

| 开关 | 展示内容 | 生效范围 |
| --- | --- | --- |
| 显示 ASN | 例如 `AS64500` | 所有节点的首页卡片、列表、详情页 |
| 显示运营商 / 机构 | 所选来源返回的网络机构名称 | 同上 |
| 显示 IP 类型 | 例如机房、家宽、商业 | 同上 |

开关只控制展示，不影响后台查询和缓存，不修改 Komari 原有手写标签。关闭的属性不会继续出现在标签的悬浮提示里；三个开关全部关闭时隐藏整个 IP 标签区域。IPv4 和 IPv6 分别展示，避免把不同地址的类型混在一起。

### 类型含义

查询方式和中文分类参考 [IPQuality](https://github.com/xykt/IPQuality)。优先读取 IPinfo 的网络使用类型；缺失时才参考同一来源的公司类型，不根据机构名称猜测。

IPregistry 按[官方响应字段](https://ipregistry.co/docs/responses/ip-address-fields)读取网络 ASN、机构和网络类型；网络类型缺失时参考公司类型。沿用下表中对应的中文分类，另将 inactive 显示为“未活跃网络”。不根据移动运营商名称或安全检测标签补猜网络类型。

| IPinfo 分类 | 标签 |
| --- | --- |
| 运营商网络（ISP） | 家宽 |
| 托管网络（hosting） | 机房 |
| 商业机构（business） | 商业 |
| 住宅用途（residential） | 住宅网络 |
| 移动接入（mobile） | 移动网络 |
| 教育 / 政府 | 教育 / 政府 |

“家宽”沿用 IPQuality 对运营商网络的展示口径，是数据库标签，不是物理家宽或宽带套餐的认证。“商业”不等于“商宽”，不会改名为商宽。缺少类型时省略该标签，ASN 或机构信息仍可独立显示。

### 自动更新与手动刷新

- 默认每 24 小时更新，可设为 1 至 720 小时。后台每 10 秒检查队列，一次查询一个地址；每次查询完成后至少等待 60 秒，随后在下一轮检查时查询下一个地址。请求未结束时不启动另一条查询；多个节点使用相同地址时共用一次查询。
- “刷新 IP 信息”只刷新全部节点的 IP 信息，不派发回程任务。手动队列跳过正常缓存、单地址失败等待和全局限流冷却，但仍遵守查询完成后至少等待 60 秒的间隔；关闭自动查询后仍可手动刷新。
- 按钮提示任务已入队，不代表查询完成。主题自动读取后续结果，重复点击不会重复加入尚未完成的同一地址。
- 普通查询失败后，该地址从查询完成起至少等待一小时再自动重试，其他地址不受影响。收到 HTTP 429 时，整个自动 IP 查询队列从收到响应起固定冷却一小时；再次收到 429 仍从本次响应起等待一小时，不逐次增加冷却时长。手动查询成功不会提前解除自动队列的冷却。
- 同来源的旧结果保留，并显示失败原因。管理员在节点详情中可看到全局限流状态及自动查询恢复时间（UTC）；游客不显示全局调度信息。不同来源或不同 IP 的旧结果不会用于当前地址。
- 手动队列、查询间隔和限流恢复时间在插件重载后保留，重载不重新计算或延长冷却。节点移除或换 IP 后，不再执行不适用的旧任务。取消回程节点选择不会取消 IP 查询。
- IP 查询与回程分别调度；回程配置无效、目标为空、NextTrace 缺失或回程任务失败，都不会阻止 IP 查询。

## 三网回程检测

在“主页延迟检测”中选好探测点并保存即可，无需再配置一份回程地址。插件通过 Komari 的现有接口读取当前主题设置和探测任务，不需要修改 Komari 本体。

- 三网模式优先使用每台服务器的完整单独配置，否则继承全局三项默认探测点，显示顺序跟随主页。
- 迷你卡片和列表仍使用单线路绑定。后台同时覆盖已配置的单线路和三网探测点，同一服务器选择了同一个探测点时只检测一次。
- 每个探测点执行一次 NextTrace，不因为域名同时支持 IPv4、IPv6 而拆成两次。域名由被测节点解析；固定 IP 使用对应版本。
- ICMP 任务使用 ICMP 探测；TCP 任务使用原地址的端口，未写端口时为 80；HTTP / HTTPS 任务提取主机和端口，以 TCP 探测回程，默认端口分别为 80 和 443，不请求网页路径。
- 探测点已删除、地址无效或未绑定对应服务器时，显示原因并跳过该项，不用模拟延迟或其他地址代替；其余有效探测点继续检测。
- 修改主页选择或后台探测地址后，下一轮读取与调度自动使用新配置，旧目标结果不再显示，也不再派发旧排队任务。已发出的任务会被收尾，不当作新目标的结果。

例如主页使用 TCP 目标 `example.com:443`，可在参与检测的节点检查 NextTrace 是否可用：

```sh
LC_ALL=C timeout -k 5s 90s nexttrace -j -T -p 443 -q 1 -m 30 -n -M example.com
```

示例域名仅说明命令格式，验证时应替换成主页探测点的实际地址。路由探测通常需要 root 或相应网络权限。NextTrace 路径默认是 `nexttrace`，也可指定如 `/usr/local/bin/nexttrace` 的绝对路径；插件不自动安装它。

- 开启“检测全部节点”时检测全部节点；关闭后可搜索并勾选指定回程节点，支持全选当前搜索结果及清空选择。这份选择只影响回程。
- 默认间隔为 360 分钟，可设为 5 至 43200 分钟。后台每 10 秒检查到期任务，默认最多同时检测 2 台节点，同一节点一次执行一个目标。
- 间隔从上次完成或失败起算，任务多时会排队，不保证在到期的同一秒启动。无需持续打开网页。
- 设置中的“检测回程”和首页原有刷新入口都只刷新所选节点的回程。关闭自动检测仍可手动执行，不附带查询 IP 信息。
- 单次 NextTrace 最多运行 90 秒，额外预留 5 秒终止时间。180 秒内未收到探针结果会记录失败。关闭自动检测不撤销已派发或手动排队的任务。

## 设置保存

两个设置区域分别展示，但继续与其他主题设置一起通过页面顶部的“保存设置”提交；顶部“重置”撤销未保存修改。手动刷新使用已保存配置，有未保存修改时先保存。

也可以在 Komari 插件配置页修改同一份配置。不要同时在两边编辑；已打开的另一页需重新读取。网络配置保存失败时不会继续提交其他主题设置；网络配置成功、其他主题设置失败时会明确提示，未成功的修改保留供重试。

## 结果含义

- 三网回程规则沿用 0.3.0，参考 [TcpQuality 的 c2295ae 版本](https://github.com/ibsgss/TcpQuality/tree/c2295ae)。按跳数排列可见地址、合并重复地址，结合 ASN、骨干前缀和前后转接关系判断，不只选择目标运营商或最后看到的网络。
- 电信支持 CN2GIA、CN2GT、CTGGIA、163；联通支持 10099、9929、4837，以及 `10099->9929`、`10099->4837`、`163->4837` 等组合；移动支持 CMIN2、CMI 及转联通组合。三段组合按 TQ 规则压缩为首尾两段。
- CN2GIA、CN2GT、CTGGIA 和由地方接入推断的 4837 是路径规则结论，不是商业套餐认证，也不保证所有中间跳点都可见。
- 缺少 ASN 的 `2408:8120:` 优先识别为 9929，不被更宽的 `2408:` 归为 4837。回程中的 ASN 仍来自 NextTrace，未改用 IPinfo 或 Team Cymru；修改节点 IP 标签不会改变回程判断。
- 主题展示插件给出的最终线路标签；没有可识别路径时显示“无法确定”。已有跳点缓存仍会按现有规则重算，不改变检测时间，不因此派发新任务。
- 中间跳点未响应但明确到达目标时视为检测完成；未确认到达、非正常退出或节点离线时保留相应状态。失败不沿用旧线路冒充本次结果。旧版 NextTrace 未报告到达状态时不宣称已到达。
- 使用主题 v1.14.1 及更新版本时，大卡片、小卡片、迷你卡片把对应线路放在丢包率进度条上方左侧，丢包率数值位于右侧；三网模式逐行匹配探测点。列表没有丢包率条，继续显示回程摘要。详情页按探测点名称展示目标、时间和结论；登录管理员可展开具体跳点。回程不显示“过期”文字，但保留时间、正在更新和失败信息。
- 探测点名称明确标注电信、联通或移动时，作为相应路径规则的方向提示；名称无法确定运营商时，只按可见路径判断，不按三条线路的排列位置猜测。

## 游客权限与存储

IP 信息和回程各有独立游客开关，默认关闭。后台按各自设置返回结果，并始终过滤隐藏节点；游客结果不包含节点完整 IP 或详细跳点。Komari 自身的私有站点规则和 2FA 不变。

结果与队列保存在 Komari 的插件长期数据目录，支持重启后继续处理。升级保留长期数据，卸载时按 Komari 的规则删除。缓存使用两个交替快照并兼容旧快照，不直接覆盖旧版只读文件。

独立手动接口：

- `POST /api/admin/lumina-network/v1/ip-refresh`：只刷新全部节点的 IP 信息。
- `POST /api/admin/lumina-network/v1/run`：只检测所选节点的回程。
- 旧 `POST /api/admin/lumina-network/v1/detect`：保留为仅回程入口，不再同时刷新 IP。

## 开发与验证

在主题源码目录运行：

```sh
npm run test:network
npm run test
npm run typecheck
npm run lint
npm run package:network
```

在相邻 Komari 源码目录还可运行：

```sh
go run ../Komari-Theme-LuminaUltra/network-plugin/tests/goja-check.go
```

它使用真实 Komari JavaScript 运行时验证加载、缓存和独立查询入口，探针与外网请求使用替身。实际回程及节点权限仍需部署后验证。

本地放有 TcpQuality 源码且已安装 Bash、awk 时，可运行：

```sh
node network-plugin/tests/compare-tcpquality.cjs ../TcpQuality/runTcpQuality-core.sh
```

对照仅提取 TQ 的纯判断函数，不执行安装、网络探测或报告上传。固定样本包含 46 组路径，其中 45 组预期与参考版本一致，1 组保留 IPv6 联通精品精确前缀修正。测试使用示例地址，不包含真实节点资料。
